# kb-v2 开发手册

> 个人知识库（Knowledge Base）项目开发记录。本文档沉淀**核心机制设计与调优决策**，配合《踩坑手册》阅读。
> 项目：FastAPI + LangGraph + ChromaDB + bge-small-zh + BM25 + Reranker + 知识图谱

---

## 1. 项目概览

- **定位**：个人笔记知识库问答系统，131 篇原始笔记 → 6786 个片段 → 支持限定领域/全库两种检索模式 + 多 Agent 问答（Planner → 检索 → 回答 → Reviewer）。
- **检索链路**（核心）：
  ```
  问题 → 向量召回(k×8) + BM25关键词召回(30) + 图谱关联文档召回
       → 融合排序 → Reranker 前50加分微调(weight=0.25) → top_k 截断
  ```
- **Benchmark 现状**（23 例刁钻题，2026-09-13 实测）：
  | 口径 | hit@1 | hit@3 | Recall@5 | MRR |
  |---|---|---|---|---|
  | 限定领域 | 0.913 | 0.957 | 0.957 | 0.928 |
  | 全库 | 0.652 | 0.783 | 0.783 | 0.696 |

## 2. 检索链路设计（三路召回 + 融合 + 重排）

### 2.1 为什么是三路召回

单一向量检索的盲区：
1. **专有名词/术语**：语义近邻把 "LangGraph" 的精确命中挤掉 → 需要 BM25 关键词通道。
2. **整本书型 PDF**：一本书几百个 chunk，正确答案 chunk 的向量分系统性偏低，top_k 直接漏掉 → 需要**扩大候选池 + 关键词/图谱保底**。

### 2.2 融合策略：加分并入，不改分数尺度

- 向量分 = `1 - distance`（0~1）。
- BM25：命中查询词数比（0~1）× `bm25_boost`（0.10）并入 score。
- 图谱：命中即加 `graph_boost`（0.08），保证关联文档片段进前排。
- 排序由融合分主导，各通道只做**加分微调**——不颠覆主排序，避免"哪个通道权重高谁就赢"。

### 2.3 关键参数（当前值 + 调参依据）

| 参数 | 值 | 依据 |
|---|---|---|
| `fetch = k × 8` | 8 | 候选池 25→40：整本书 PDF 正确章节常排融合分 30 名外，rerank 窗口必须能覆盖到 |
| `bm25_top_k` | 30 | BM25 10→20→30：PDF exact match 片段更多进池（注：单靠它提升有限，见踩坑手册#6） |
| `rerank.top_n` | 50 | 精排窗口 30→50：PDF 正确章节实测排融合分 15~22 名，30 名窗口偶有覆盖但不够 |
| `rerank.weight` | 0.25 | 加分权重 0.15→0.25：让 rerank 中分片段（0.5 左右）有更大机会翻进前排 |
| `graph_boost` | 0.08 | 图谱关联文档加分，命中即加 |

### 2.4 Reranker（交叉编码器）

- 模型：`BAAI/bge-reranker-base`（中文交叉编码器，约 1GB，需镜像下载）。
- 只对**融合排序前 top_n 条**打分（全库 6786 条逐一打分不可行）。
- **加分微调而非直排**：交叉编码器对中文短文本打分普遍偏高且集中（0.85~0.99），直接按 rerank 分排序会把融合排序的正确结果打乱（实测 async_03 从第 1 被打到第 7）。改为以池内最低分为基线，`分差 × weight` 并入融合分。
- 模型不可用 → 静默降级原排序，检索链路永不中断。

## 3. 知识图谱（KG）设计

### 3.1 两层架构

| 层 | 内容 | 构建方式 |
|---|---|---|
| 元数据层 | doc / topic / tag 节点 | **零 LLM**：从文档元数据直接构建，1259 节点/2202 边 |
| 实体层 | 实体-关系-实体三元组 | LLM 增量抽取（`KG_EXTRACT_PROMPT`），只处理新增/变化文档 |

### 3.2 检索增强

`_search_by_graph`：问题命中图谱实体/标签 → 拉关联文档片段（一跳 + 二跳 `expand_sources`）→ 带 `graph_boost` 进候选池。解决"标签对但向量分排不进前排"的漏检。

### 3.3 前端

- 默认只显示主干（doc/topic/tag 251 节点/904 边），实体层默认隐藏按需勾选。
- 领域圆周分簇初始化：领域均布圆周 → 文档挂领域扇区 → 标签/实体内环。
- 力导向参数：弹簧 rest 70→100、引力 0.012→0.006、边透明度 0.10→0.055、标签门槛 deg 6→8。

## 4. 工具池设计

- `kb/agents/tool_pool.py`：`ToolSpec` / `ToolPool` / `get_pool()` 单例（register / schemas / call / stats / names / list_all）。
- 4 个工具：`search_knowledge`（检索）、`execute_python`（执行）、`web_search_tool`（联网）、`search_graph`（图谱检索）。
- 兼容性：`TOOLS` / `TOOL_FUNCS` 由池派生，`graph.py` 白名单只放 execute_python + web_search_tool，不受影响。
- **设计定位**：本地版工具池（JSON Schema 声明 + 执行器映射），未来接 MCP 只需池内工具包 `@mcp.tool()`。

## 5. Benchmark 评估方法论

### 5.1 用例集

23 例刁钻题，7 组：decorator / async / agent / react_confusion / agent_confusion / vector_db / pydantic。
每组含"混淆"用例——问题听起来像 A 领域实际答案在 B（如 "ReAct 框架" 不能命中 React.js 前端教程）。

### 5.2 指标口径

- `hit@1/3/5`：期望 source 是否在 top k。
- `MRR`：期望 source 排名的倒数均值。
- `Recall@k`：单答案场景下 **Recall@k == hit@k**（口径已在输出中注明）。
- filtered（限定领域）与 global（全库）双口径，global 更难。

### 5.3 标注有效性校验（重要！）

Benchmark 用例的 `expected_source` 必须**内容真实存在**。本次发现 4 个无效标注：
- 期望源 `AI-Agents-in-Depth-zh-CN.pdf` 全书 316 片段中 "LangChain" 仅 4 处（非教程）、“ReAct prompt” 0 处、“langgraph” 3 处。
- 检索不可能找到不存在的答案 → 用例永远 0 分 → **测的不是检索能力**。
- 修正方式：全文扫描（`_collection().get()` + 关键词计数）定位内容真实存在的文档，逐一改标并写明依据（见 retrieval_cases.json 各用例 note）。

**修正前后对照**（同参数下）：filtered hit@1 0.826 → 0.913。

## 6. 评估与延迟现状

- `tests/agent_eval.py`（50 例端到端问答评估）：source_hit 0.846 / answer_hit 0.82 / domain_match 0.714 / tool 1.0。
- RAG 组 answer_hit **0.974**（39 例几乎全对），但**平均延迟 20.3s** 是主要短板（avg prompt 4018 token + DeepSeek 推理）。
- 优化方向（未做，待用户确认）：prompt 瘦身（检索片段截短、只留 top3）、rerank 缓存/按需、换低延迟模型。

## 7. 性能优化（图谱前端）

- 力导向 O(n²) 斥力（1259 节点 = 158 万对/帧）→ **网格空间分区**（cell = max(70, minD×4)，只算同格 + 邻 8 格，O(n·k)）。
- 2202 条边逐条 stroke → 一次 path 批量 stroke + 高亮层。
- 动画帧数自适应：>600 节点 350 帧 / >300 节点 500 帧 / 默认 900 帧。
- 拖拽：mousemove 高频直绘 → **rAF 渲染循环节流**（一帧最多一次重绘，拖拽中隔帧跑轻量物理）。
